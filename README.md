# Warehouse Simulator

倉庫管理 + 2Dレイアウト作成 + 物流シミュレーションのWebアプリケーション。
実際の倉庫を2Dマップ上に再現し、**入庫 → 保管場所決定 → フォークリフト搬送 → 出荷完了**
までの動きを画面上で検証できる「倉庫のデジタルツイン」を目指しています。

現在の実装状況:
- **2D倉庫エディタ完了**（ラック配置・ロケーション自動生成・保存/読込）
- **複数エリア構成**（L字・コの字・別棟接続などの自由形状倉庫）完了
- **エリア間の接続口・シャッターと経路探索の連動**完了
- **物流シミュレーション完了**（倉入れ → フリーロケーション → 保管 → 出庫 →
  出荷ゲート → 空ラック化 → 積み重ね までのイベント駆動シミュレーション）
- KPI集計・ボトルネック分析・レイアウト比較まで実装済み

## 1. 技術構成

| 領域 | 採用技術 | 選定理由 |
| --- | --- | --- |
| フロントエンド | React 18 + TypeScript + Vite | 型安全・高速なHMR |
| 2D描画 | Konva.js (react-konva) | 図形の選択/変形/ドラッグが標準装備。CAD的な編集に向く |
| 状態管理 | Zustand | ボイラープレートが少なく、Undo/Redoなどを素直に書ける |
| バックエンド | Node.js + TypeScript + Express | フロントと同一言語でドメインモデルを共有できる |
| データベース | SQLite (`node:sqlite`) | Node標準機能のためネイティブビルド不要。標準SQLのみ使用しPostgreSQL移行に備える |
| 経路探索 | 自前実装のA* (8方向 + 経路直線化) | 倉庫特有のコスト（歩行者エリア回避・車体クリアランス）を扱うため |
| テスト | Vitest | ドメインロジックとAPIの回帰テスト |

**モノレポ構成（npm workspaces）**にして、ドメインモデルとシミュレーションエンジンを
`@ws/shared` に集約しています。UIから独立しているため、
将来サーバ側でのバッチシミュレーションやレイアウト最適化（Phase 8）にも同じコードを再利用できます。

### Windows での開発開始方法（コマンド入力なし）

1. **Node.js をインストールする**
   [https://nodejs.org/ja/download](https://nodejs.org/ja/download) から
   **22 LTS もしくは 24 LTS** をダウンロードしてインストールします。
   （このプロジェクトは Node.js 標準の `node:sqlite` を使うため **22.5.0 以上**が必要です）
2. **souko フォルダを開く**
3. **`dev.bat` をダブルクリックする**
4. **ブラウザが自動的に開きます**（`http://localhost:5173/`）

以降、コードを変更するとブラウザに自動で反映されます。
**変更のたびに起動し直す必要はありません**（Vite の HMR と `tsx watch` が効いています）。

`dev.bat` は次を自動で行います。

- Node.js と npm が入っているかの確認（無ければ、入れ方を表示して停止）
- `node_modules` の確認 → **無いときだけ** `npm install` を実行
- ポート 5173 / 5178 の空き確認（すでに起動中ならブラウザだけ開く）
- 開発サーバーの起動 → 起動完了を待ってブラウザを開く

#### 用意しているバッチファイル

| ファイル | 用途 |
|---|---|
| **`dev.bat`** | **メインの起動用。ふだんはこれだけ使います** |
| `start.bat` | `dev.bat` と同じ動作（名前で迷わないように用意） |
| `stop.bat` | 開発サーバーを停止する |
| `restart.bat` | 停止してから起動し直す |
| `update.bat` | 最新版に更新する（`git pull` ＋ 必要なときだけ `npm install`） |
| `check.bat` | Node/npm のバージョン、依存関係、型チェック、テスト、ビルドをまとめて確認 |

どれも置かれているフォルダを基準に動くので、**フォルダを移動しても、パスに日本語や空白が含まれていても動作します**。
エラーが起きたときは原因と対処をウィンドウに表示し、すぐ閉じないように一時停止します。

> `stop.bat` は「Node.js のプロセスを全部終了」といった乱暴なことはしません。
> **このプロジェクトのフォルダから起動された `node.exe` だけ**を対象にします。

> `start.bat`（開発サーバー）と `npm start`（本番ビルドの配信）は別物です。
> 開発中は `dev.bat` / `start.bat` を使ってください。

> `update.bat` は Git で取得したフォルダでのみ使えます。
> zip を展開して使っている場合は、zip を取り直してフォルダごと入れ替えてください。
> 未コミットの変更があるときは、上書きしないよう更新を中止します。

            │            │        ├── RackSpec（列数・段数・最大収納数・採番ルール・受入ラック種別）
            │            │        ├── InboundGateConfig / OutboundGateConfig
            │            │        └── EmptyRackYardConfig
            │            ├── Location（ロケーション番号・座標・作業位置・最大収納数・所属エリア）

### 物流シミュレーション

ゲートに設定した数量・割合が、そのまま実際のイベントを生み、
フォークリフトが動き、在庫・ラック・ロケーション・ゲートの状態が変化する。

```
倉入れ口（1日◯本 / サイズ別割合 / 時間帯別割合 / 使用ラック割合）
   ↓ イベント生成（端数は最大剰余法で配分し合計が一致）
荷受け（ゲート能力 本/時・同時搬入台数）
   ↓
フリーロケーション判定（サイズ適合・空き容量・優先エリア・出荷頻度・搬送距離）
   ↓ A*で通路を通って搬送
保管（ロケーション状態: 空 / 一部在庫 / 満載）
   ↓
出荷指示（ボリューム区分の割合 → 1オーダー本数 → サイズ別明細）
   ↓ 在庫を先入れ先出しで検索
出荷ゲートへ搬送 → ゲート前で滞留 → 能力に従って出荷
   ↓
ラックが空になる → 空ラック置き場へ搬送 → 積み重ね（種別ごとの段数上限）
   ↓
空ラックは倉入れ口で再利用（循環）
```

| モジュール | 役割 |
| --- | --- |
| `sim/eventGeneration.ts` | 数量・割合・時間帯から入出庫イベントを生成（決定論的乱数） |
| `sim/slotting.ts` | フリーロケーション（選択ルールは差し替え可能） |
| `sim/racks.ts` | 可搬ラックの積載・状態遷移 |
| `sim/stacking.ts` | 空ラックの積み重ね管理 |
| `sim/engine.ts` | イベント駆動の本体（車両・ゲート・タスク・在庫） |
| `sim/heatmap.ts` | 走行・渋滞・作業・搬送距離の分布（ヒートマップ） |
| `sim/analysis.ts` | ボトルネック分析とレイアウト比較 |

### ヒートマップ

シミュレーションの走行データから、4つの切り口で分布を可視化する。
左パネルで切り替え、2Dマップ上に重ねて表示する。

| レイヤー | 何を測るか | 読み方 |
| --- | --- | --- |
| 通行量 | フォークリフトの走行距離を通過セルへ按分 | 太い動線＝主要通路 |
| 渋滞・待機 | 車両の停止時間（対向車待ち・バース待ち）＋ゲート前のラック滞留 | 濃い場所＝詰まっている場所 |
| 作業集中 | 荷役（格納・取得・積み重ね）に費やした時間 | 作業が集まる場所 |
| 搬送距離 | その保管場所を目的地とした作業の走行距離 | 濃い場所＝遠い保管場所＝配置見直しの候補 |

配色は**1レイヤーにつき1色相の連続スケール**（薄い=少ない → 濃い=多い）で、
OKLCH 明度が単調に下がることを検証済み。マップのラックが青系のため、
ヒートマップ側では青を使わない（通行量=オレンジ / 渋滞=レッド / 作業=バイオレット / 距離=マゼンタ）。

ヒートマップのホットスポットはボトルネック分析にも使われ、
「本棟 出荷ゲートB付近 (13, 34)で待機が発生しています」のように**場所を名指しで**報告する。

**ラックの2つの概念**: レイアウト上の「保管ラック構造」(`RackObject` — ロケーションを生成する棚)と、
商品を積んで運ばれる「可搬ラック」(`RackUnit` — タイヤラック/カゴ台車)を分けている。
出荷で空になるのは可搬ラックで、これが空ラック置き場へ運ばれて積み重なる。

### 倉庫の形（複数エリア構成）

倉庫を1つの長方形として扱わず、**複数の Area を組み合わせて実際の倉庫形状を再現**する。

| エンティティ | 役割 | 主なフィールド |
| --- | --- | --- |
| `Area` | 倉庫を構成する区画（本棟・増築棟・屋外ヤードなど） | 形状（矩形/多角形の頂点列）、位置、回転、種別 |
| `AreaConnection` | エリア間の接続口 | from/to エリア、位置、開口幅、厚み、角度、通行可否 |
| `Shutter` | 接続口に設置するシャッター | 接続口ID、名称、状態（open / closed） |

- **エリアの外は進入不可**。外壁沿いは車体クリアランス分だけ走行できない。
- **エリアが隣接しているだけでは通行できない**。接続口がある場所だけがエリア間の通り道になる。
- **シャッターを閉じるとその接続口を通る経路が探索されなくなる**（A* のセル遷移判定に反映）。
- 倉庫総面積は全エリアの**和集合**で計算するため、重なった部分を二重計上しない。
- Area は Layout に属するため、レイアウトA/Bで**建屋の形そのものを変えて比較**できる（増築案の検証）。

エリアは将来 `kind` で 別棟 / 増築部分 / 屋外ヤード / 中2階 へ拡張でき、
Shutter も独立エンティティなので サイズ / 開閉時間 / 防火シャッター / 通過可能車両 を後から追加できる。

| エンティティ | 役割 | 主なフィールド |
| --- | --- | --- |
| `Warehouse` | 倉庫の実寸と表示設定 | 幅/奥行(m)、縮尺(1m=Npx)、グリッド、構内制限速度 |
| `Layout` | 倉庫の「配置案」。A/B比較の単位 | 名称、複製元 |
| `LayoutObject` | マップ上の配置物（種別ごとの合併型） | 座標・サイズ・回転、走行可否 |
| `RackObject` | ラック/棚 | `RackSpec`（列数・段数・ピッキング面・採番ルール） |
| `Location` | ロケーション | 番号、列/段、中心座標、**作業位置**、最大収納数 |
| `Product` | 商品マスタ | サイズ・重量・**出荷頻度**（高/中/低回転） |
| `Inventory` | ロケーション別在庫 | 数量、入庫日、ロット |
| `Forklift` | 車両 | 最大速度・加減速度・最大積載重量・状態・向き |
| `Task` | 作業単位 | 入庫格納/取出、始点・終点、割当車両、所要時間 |
| `Simulation` | 実行設定と結果 | 開始時刻、刻み、制限速度、集計指標 |
| `SimulationEvent` | 時系列ログ | 時刻、種別、車両、ロケーション |

**座標系**: ドメイン層の座標・寸法はすべてメートル。ピクセル変換は表示層のみが行います。
原点は敷地の左上、回転はKonvaと同じく `(x, y)` を中心とした時計回りです。
`LayoutObject` と `Location` は中心座標から所属エリア（`areaId`）が自動判定され、
エリア別の在庫・ロケーション集計に使われます。

`Location.approachX/Y` は「フォークリフトが停車する通路側の作業位置」で、
ラックのピッキング面と回転角から自動計算されます。経路探索はこの点を目的地に使います。

### 永続化

SQLiteに正規化して保存します（`packages/server/src/db/database.ts` のマイグレーション参照）。
ラック仕様・フォークリフト諸元のような可変スキーマ部分のみ `props` にJSONで格納し、
検索対象になる `locations` は完全に正規化しています。
SQLiteの独自構文を使わないため、PostgreSQLへは接続層の差し替えだけで移行できます。

| エリアの移動 / 拡大縮小 | 選択してドラッグ / 右パネルの ±10% ボタン・数値入力 |
| 接続口の作成 | 「⇔ 接続口を追加」ツール → 接続する2つのエリアを順にクリック |
| シャッターの設置・開閉 | 接続口を選択 → 右パネルで「シャッターを設置」→「閉じる / 開ける」 |

初回起動時は、以下のサンプル倉庫が自動生成されます。

- **本棟**（60×40m）: 北側の倉入れ口A、南側の出荷ゲートA/B、ラック6本（180ロケーション）、
  空ラック置き場、フォークリフト3台
- **増築棟**（18×24m）: ラック2本（36ロケーション）、出荷ゲートC
- 両者をつなぐ**連絡通路（シャッター付き）**

シャッターを閉じてから「経路確認」で本棟→増築棟のルートを引くと、
経路が見つからなくなることを確認できます。

## 6. 将来拡張への備え

- **RFID / バーコード / ハンディ端末 / IoT**: 位置情報は `ForkliftRuntime` に集約しているため、
  実機のトラッキングデータをそのまま流し込めます。
- **CSV/Excelインポート**: `@ws/shared/io` に依存ライブラリなしのCSVパーサを実装済み
  （BOM・CRLF・引用符対応）。商品マスタ・在庫・ロケーションの取込に使用します。
- **PostgreSQL移行**: SQLは `packages/server/src/repositories/` に閉じ込め、標準構文のみ使用。
- **AIレイアウト最適化**: シミュレーションエンジンがUIから独立しているため、
  ヘッドレスで多数のレイアウト案を評価できます。
